# 统一代码审查比较、验证与行动报告

## 0. 结论摘要

本报告基于提交 `0976fc88080c514dd72f9da4fe1016e638bc15bc`，统一处理 Claude、Codex、DeepSeek、Qwen 四份报告。原报告保留不变；59 个正式编号问题已在[标准化明细](统一代码审查标准化明细.md)中逐字段转录。

核心结论：

- **P0：0 项。** 未发现已经构成安全事故、已发生数据丢失、大范围不可用或不可恢复后果的证据。
- **P1：5 项。** 分别是 POSIX 重定向绕过危险 Git 守卫、凭据/命令泄露、同仓库多活动任务歧义、state/event 半提交、全树指纹重复哈希导致核心流程性能故障。
- **P2：16 项。** 主要是发布清单、生命周期、Hook 注册/启动、配置契约、可观测性和供应链加固。
- **P3：27 项。** 其中包含需基准或产品决策的低收益项，以及 8 项可直接判为误报。

最重要的编辑结论是：**报告原严重程度不能直接用作修复顺序。** 例如 Qwen 把 POSIX parser 问题定为 P2 且称“偏保守”，实际 Hook 复现证明它能放行 `reset --hard`；相反，Claude 把当前 Codex matcher 和 PreToolUse schema 判成高风险错误，但当前官方契约与现有测试均证明这两项是误报。

### 0.1 术语与状态

- **报告原始观点**：只复述原报告，不代表采纳。
- **代码验证结论**：结合当前代码、调用路径、现有保护、定向测试或复现实验后的结论。
- **已确认**：代码和实际触发路径均可证明。
- **部分成立**：代码事实成立，但触发范围、影响或修复建议被原报告夸大/写错。
- **需要运行验证**：静态条件存在，但缺少目标宿主、文件系统或规模环境证据。
- **误报**：当前代码、官方契约或实际测试否定原结论。
- **重复问题**：仅用于标记原始条目已并入某统一问题；统一表本身不重复计数。
- **暂不处理**：事实可能存在，但没有实际影响、收益不足或需要先做产品决策。

### 4.1 仍需人工判断的分歧

1. **模块边界**：是只抽取共享常量，还是连 scope/task lookup 一并拆分。建议先做依赖图和多平台启动基准，再批准结构性重构。
2. **Hook fail-open 可观测性**：stderr 单行诊断、私有滚动日志、还是仅 debug 模式。需要在“可诊断”和“避免泄露/宿主噪音”之间定产品策略。
3. **cross-platform 支持措辞**：在真实 Windows Codex host smoke 未闭环前，是降级为“目标支持”，还是保留“支持”并显式列证据缺口。
4. **locale**：中文是否是该插件的产品默认，是否需要配置化。原报告不能替产品做决定。
5. **cmd 顶层方言**：必须在真实 Windows Codex host 确认顶层 `%VAR%` 是否由 cmd.exe 隐式展开，再决定 U-021 是否修复。

## 6. 代码验证范围与证据

验证严格限定为：

1. 多报告共识；
2. 任一报告 P1；
3. 单报告但涉及安全、数据、并发或发布供应链；
4. 报告间存在冲突；
5. 为判断上述问题而必须核对的直接保护机制。

没有借此重新展开全库审查。验证使用当前源码、clean `git archive HEAD`、临时仓库/数据目录、故障注入、原生 Windows cmd 实验、现有定向测试，以及当前官方 Codex Hook 契约。临时复现没有写入项目文件。所有实际运行的现有定向测试均通过；通过并不否定问题，因为多项问题是现有测试未覆盖的负向场景。

### 6.1 P1：U-001 POSIX 重定向可绕过危险 Git 守卫

**报告原始观点**

Qwen QW06 认为 `>>` 被误当作段分隔符，主要是解析精度问题，整体“偏保守”、影响有限。

**代码与调用关系**

- 问题代码真实存在于 `hooks/dev_flow_hook.py` 的 `_posix_segments`；`_SEPARATOR_CHARS` 包含 `<`、`>`。
- tokenizer 把重定向操作符、文件描述符和目标拆成新“命令段”；下游 `_git_invocations` / `_parse_git` 因此看不到完整 Git argv。
- 该结果进入 PreToolUse 的 `command_denial_reason`；返回空即放行，问题会在真实 Hook 路径执行。

**上游/下游保护**

- 重定向位于完整危险命令之后时，前段仍可识别。
- strict wrapper 不能修复同一分段器的问题；静态 `bash -lc` payload 也会走到该解析逻辑。
- 没有针对重定向前置、中置、fd 重定向的现有回归测试。

**触发与证明**

在有活动 `INTAKE` 任务的实际 Hook 调用中：

- `git reset --hard HEAD > out.txt`：拒绝；
- `> out.txt git reset --hard HEAD`：**放行**；
- `2>/dev/null git reset --hard HEAD`：**放行**；
- `git > out.txt reset --hard HEAD`：**放行**；
- 等价的静态 `bash -lc` 前置/中置重定向：**放行**。

这是合法 POSIX shell 语法，不依赖动态 `eval`。

**修复评价与兼容性**

Qwen“标记已知限制”不够。应正确识别 redirection 并跳过 fd/operator/target，同时保留 simple command 的 executable 和普通参数；短期也可对“含重定向且疑似执行 Git、无法可靠解析”的命令 fail-closed。兼容风险中高，必须覆盖 `2>&1`、`<&`、`>|`、heredoc、here-string、nested shell 等，避免粗暴拒绝正常命令。

**代码验证结论：已确认，P1，成本 M。**

### 6.2 P1：U-002 敏感 remote、命令和 stderr 未脱敏

**报告原始观点**

Claude CL03 与 Codex CX03 均认为 credential-bearing remote 会进入 state/output；Codex 进一步指出 mutation command、quarantine 和 raw stderr。

**代码与调用关系**

- `_remote_url` 返回 `git remote get-url` 原值，preflight 将其写入状态；`command_show` 返回完整 state。
- `_begin_mutation_intent` 保存完整 command；`_run` 错误详情包含完整命令和 stderr。
- 未找到统一 redactor/scrubber。
- 这些路径都在正常 preflight、show、mutation 和异常处理流程中执行。

**保护**

- state/data 目录的 0600/DACL 能限制其他本地账号，但不能阻止值进入 stdout、模型上下文、会话记录、备份和支持包。
- evidence hash 只证明内容未变，不等于脱敏。

**触发与证明**

临时 Git remote 使用非真实 marker credential；preflight 后 `state.json` 和 `show` 输出都包含 marker。未把真实 token 写入测试。

**修复评价与兼容性**

只把 URL userinfo 替换成 `<redacted>` 不足以绑定后续 fetch，也可能忽略敏感 query。推荐保存脱敏 display + 完整 URL 的不可逆摘要；fetch 时重读 live URL、比较摘要后使用 live 值。命令/quarantine/stderr 需要同一 secret scrubber。该改动会改变 evidence 内容，需 bump 证据契约，并迁移或作废在途审批证据。

**代码验证结论：已确认，P1，成本 M–L。**

### 6.3 P1：U-003 同一源码仓库可同时被多个活动任务占用

**报告原始观点**

Codex CX01 指出 start 只去重单次请求，不建立跨任务 repository claim；Hook 从多匹配中取更新时间/版本最大的任务。

**代码与调用关系**

- `scripts/dev_flow.py` 的 start 路径只校验本次 request 内的 common-dir 重复与 task-id 冲突。
- `find_active_task_for_cwd` 枚举所有 state，返回 `updated_at/revision` 最大项。
- Hook 的权限、上下文和分支判断使用这个单一结果。

**保护**

- 单请求内去重、task-id 唯一、state 锁都存在，但没有保护“不同 task-id 同时 claim 同一 repo”。
- 选择最新能保持确定性，不能保证选择正确的权限策略。

**触发与证明**

临时数据根分别启动 `MULTI-A` 与 `MULTI-B`，两者都指向同一 repo，均成功；Hook lookup 返回较新的 `MULTI-B`。不存在上游阻断。

**修复评价与兼容性**

应在数据根全局锁内原子执行 claim 检查、任务创建和 claim 写入；claim key 至少包括 canonical root、filesystem identity、Git common-dir。full 的只读 source 与 lite/in-place/branch 的可写 checkout 是否允许共享，需要显式规则。Hook 遇到多个旧数据匹配必须拒绝策略相关写入并给修复指引。需要旧状态迁移和 `doctor`，成本高。

**代码验证结论：已确认，P1，成本 L。**

### 6.4 P1：U-004 `state.json` / `events.jsonl` 半提交

**报告原始观点**

Codex CX02 给出故障注入；Claude在补充安全观察中也指出状态与审计事件不是同一原子提交。

**代码与调用关系**

- `_commit_state` 先原子替换 state，再 `_append_event`，最后才完成 mutation intent。
- `_append_event` 使用一次 `os.write`，没有循环处理 short write。
- 没有 outbox、event journal 或加载时的未刷事件恢复。

**保护**

- state 自身原子替换和 mutation intent 可保护部分 crash 点。
- 但 intent 没有可重建缺失 event 的持久 payload；state 已前进后无法安全回滚用户可见结果。

**触发与证明**

把 `_append_event` 故障注入为失败后，state revision 从 1 变为 2，events 仍只有 revision 1；CLI 看到失败但持久状态已改变。

**修复评价与兼容性**

推荐 durable outbox：新 state 与 pending event 作为同一原子状态提交；随后按稳定 `event_id` 幂等刷到 JSONL；load/下次 mutation 自动恢复。需要对短写循环。变更审计格式、replay/recovery 和旧任务兼容，成本高。

**代码验证结论：已确认，P1，成本 L。**

### 6.5 P1：U-005 全树指纹在核心流程重复计算

**报告原始观点**

Claude CL01 认为一次 `_fingerprint_repo` 双观测全树，review snapshot 和后期 transition 多次调用，会使中大型仓库不可用。

**代码与调用关系**

- `_tracked_worktree_manifest` 对每个 tracked regular file 做 SHA-256；untracked regular file 也被观测。
- `_fingerprint_repo` 连续做两次完整观测。
- 完整单仓库 `review-snapshot` 成功路径实际调用五次 `_fingerprint_repo`，即十遍内容观测；原报告还漏算了外层 test-currency 检查。
- `REVIEWING`、`FINALIZING`、`DONE` 正常 transition 也各自多次调用；这是核心 full-flow 可达路径。

**保护**

- 双观测和 snapshot 前中后比较能发现捕获窗口内变化，是重要 fail-closed 证据语义。
- state lock 不能阻止 IDE/build/watchers 修改仓库。
- 没有显式观测世代或进程内安全复用。

**触发与证明**

- 现有 drift 测试通过并证明中间变化会触发 `REVIEW_SNAPSHOT_CHANGED`。
- 当前 Windows/Python 3.14.6 临时 repo：100 个 1KiB tracked 文件一次指纹约 1.54s、200 次文件哈希；1000 个时约 4.26–5.80s、2000 次文件哈希。
- 没有运行原报告的 40k 文件/2GB 场景，所以“数十分钟”和“所有中型仓库不可用”证据不足。

**修复评价与兼容性**

减少重复是正确方向，但不能直接用 index OID 替代原始工作树字节（autocrlf/filter 语义不同），也不能缓存掉用于检测捕获期变化的观测点。先消除明确重复的 DONE 检查，再设计带观测世代、可安全传递的 fingerprint 结果。任何证据口径变化必须 bump `EVIDENCE_CONTRACT_VERSION` 并使旧证据失效。

**代码验证结论：部分成立，但已达到 P1，成本 L。**

## 8. 最终决策摘要

### 8.1 最值得立即处理的 5 个问题

1. **U-001：POSIX redirection guardrail bypass。** 这是唯一被实际 Hook 调用证明能把危险 Git 操作从“拒绝”变成“放行”的问题；应先加负向回归，再修 parser。
2. **U-002：敏感 remote/命令/stderr 脱敏。** 正常 preflight/show 路径即可触发；在修复前应明确禁止 credential-bearing remote，并避免把 secret 放入命令参数。
3. **U-003：跨任务 repository claim。** 当前任务权限模型建立在“一个 checkout 对应一个活动任务”的隐含假设上，但 start 没有维护这个不变量。
4. **U-004：state/event durable outbox。** 这是明确的事务缺口；任何修复都需同时定义 crash recovery、幂等和旧事件兼容。
5. **U-005：指纹观测去重。** 已在 1000 个小文件上看到单次指纹 4–6 秒量级，而核心成功路径会重复多次；必须在保留证据语义的前提下优化。

### 8.2 需要人工判断的问题

- **架构边界**：U-017/U-028/U-029 是抽共享常量、拆 task lookup，还是保留单文件。建议批准“共享常量小步治理”，暂不批准全量拆包。
- **可观测性策略**：U-015 应采用 opt-in debug、限频 stderr 还是私有滚动日志；必须先定义 secret scrub、保留期和宿主噪音预算。
- **跨平台支持状态**：U-019 在真实 Windows Codex host 证据完成前是否调整宣传措辞。
- **顶层 Windows shell 方言**：U-021 需要真实 host 结果，不能由静态代码猜测。
- **国际化默认**：U-036 是否要从“强制中文”改成 locale/config 驱动。
- **模块/证据迁移批次**：U-002、U-003、U-004、U-005 可能都需要 schema/evidence version 变化，应由维护者决定是否合并一个破坏性版本。

- U-044、U-045、U-046、U-047、U-048：均已由官方契约、现有保护或实际测试判为误报。

- U-029、U-031、U-032、U-033、U-034、U-036、U-037、U-039、U-040、U-042：低收益维护、产品取舍或缺乏实际影响。

### 8.5 推荐修复顺序

1. **先锁住安全边界**：为 U-001 写红色回归并修 parser；同时为 U-002 建立统一 redaction 测试和临时运维告警。

3. **处理证据性能**：在 U-004 的持久化契约确定后实施 U-005，先移除重复检查，再引入显式观测世代；不要简单缓存掉漂移探针。

6. **补生命周期**：U-008 的显式 release 与 doctor/uninstall-plan；不把 cleanup 塞进 cancel，不自动删除脏 worktree。
7. **做可测的局部性能/维护改进**：U-009、U-010、U-016、U-017；先用指标证明收益。
